# 7. Серверный слой с доменными эндпоинтами вместо прокси WAQI

**Статус:** принято, заменяет ADR 0004

## Контекст
ADR 0004 описывал универсальный прокси `api/waqi/[...path]` с белым списком путей. Он отдавал клиенту сырой ответ WAQI, а валидация и маппинг шли в браузере. В Next (ADR 0006) серверный код уже есть, и данные WAQI нужны прямо на сервере, для предзагрузки и `generateMetadata`.

## Решение
- Серверные функции ходят в WAQI с `WAQI_TOKEN`, валидируют ответ и маппят его в доменные типы. Эти модули помечены `import 'server-only'`.
- Наружу торчат только узкие Route Handlers в доменном формате: `/api/stations` (станции Бишкека) и `/api/stations/[uid]` (детали станции).
- Эти же функции напрямую вызывает Server Component при первой загрузке страницы.
- Кэш: запросы к WAQI идут с `fetch(..., { next: { revalidate: 300 } })`, ответы Route Handlers — с `Cache-Control: s-maxage=300, stale-while-revalidate=600`.

## Последствия
- Клиент не знает формата WAQI. Маппер, валидация и токен живут только на сервере.
- Белый список путей не нужен: произвольный запрос к WAQI через нас сделать нельзя по построению.
- Отдельный прокси для dev не нужен, `next dev` запускает Route Handlers сам.
- Смена поставщика данных меняет только серверный слой, контракт `/api/stations` остаётся прежним.
